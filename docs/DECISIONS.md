## 1. Decision Log

| Decision ID | Topic | Decision Made | Rationale & Rule Reference |
|---|---|---|---|
| **ADR-001** | LLM Authority Boundaries | LLM is restricted exclusively to text narrative generation from `VERIFIED_EVIDENCE_SNAPSHOT`. Zero authority to change state, evaluate evidence, route disputes, or approve outputs. | `PRD.md` §4 & `PROJECT_RULES.md` Rules 7 & 8. |
| **ADR-002** | Infrastructure Scope | Single-service architecture without microservices, Kafka, Redis, Celery, RAG, or vector DBs. | `PROJECT_RULES.md` Rule 5 ("Never add microservices, Kafka..."). |
| **ADR-003** | Fail-Closed Handling | Any missing evidence, contradictory telemetry, entity validator rejection, or runtime crash immediately forces state to `MANUAL_REVIEW`. | `PRD.md` §5 & `PROJECT_RULES.md` Rule 9 ("If validation fails: FAIL CLOSED -> MANUAL_REVIEW"). |
| **ADR-004** | External Gateway Submissions | External dispute submissions are modeled as SIMULATED. Approval transitions `HUMAN_APPROVAL_REQUIRED` -> `READY_FOR_SUBMISSION` (generating PDF package). A separate action transitions `READY_FOR_SUBMISSION` -> `SUBMITTED` internally; no live bank APIs are called. | `PRD.md` §2 & `PROJECT_RULES.md` Rule 2 & Rule 3 ("Never invent Razorpay APIs... mark as simulated"). |
| **ADR-005** | IP Telemetry Semantics | IP/device consistency is treated strictly as a supporting signal, not as absolute proof of identity or fraud. | `PRD.md` §3 & §11 (Q&A Defense #5). |
| **ADR-006** | Metric Measurement Boundary | Benchmark metrics formulas are documented in `EVALUATION.md`. Target numbers will only be recorded after executing evaluation scripts during Milestone 6. | `PROJECT_RULES.md` Rule 11 ("Never report target metrics as measured results"). |
| **ADR-007** | Non-Circular Evaluation A Ground Truth | Evaluation A ground-truth labels (`DEFENDABLE` / `NOT_DEFENDABLE`) are generated by an independent synthetic scenario oracle during dataset creation, *completely isolated from and prior to executing the production routing function*. | Fixes circular evaluation by ensuring system routing output is evaluated against pre-established independent labels. |
| **ADR-008** | Semantic Fact Validation | The LLM response contract strictly prohibits claims of customer intent ("intentionally committed fraud"), legal conclusions, or fraud certainty. Hard validator rejects any draft containing unsupported inferences without adding second LLM judges or RAG pipelines. | Preserves simplicity (Rule 15) while enforcing strict safety boundaries (Rule 7 & 8). |
| **ADR-009** | Standardized Money Representation | Financial amounts across data schemas, API payloads, synthetic datasets, LLM prompts, and UI are represented consistently as **major currency units** (e.g. `amount = 4999` with `currency = "INR"` represents ₹4,999). | Eliminates major/minor unit ambiguity across system components. |
| **ADR-010** | Audit Log Retention & Terminology | The system implements an application-level append-only audit log with no update or delete operations for historical entries. Rejected LLM outputs are retained in the audit log for traceability rather than being destroyed. | PRD §7 & auditability compliance. Exact wording: "The invalid output is excluded from the final evidence package and cannot progress through the workflow; the rejected output is retained in the append-only audit log for traceability." |
| **ADR-011** | Milestone 1 Schema Implementation — Python stdlib only | `backend/schemas.py` uses exclusively Python 3.10 stdlib (`dataclasses`, `enum`, `typing`). No external packages (Pydantic, attrs) introduced at this stage. Business-invariant validation (e.g. no-negative-amounts) is deferred to the routing layer, not enforced at the schema type level. Schema-level tests run via `python -m unittest`. | Keeps Milestone 1 within strict scope (no external dependencies, no business logic). Consistent with ADR-002 (minimal infrastructure). |
| **ADR-012** | Evidence Sufficiency Model — Two-Part Deterministic Check (`isSufficient`) | Replaced the prior "all five signals must be True" universal AND gate (`isStrong`) with an explicit two-part model: (1) `hasCriticalContradiction` — identity mismatch or impossible timestamps disqualify regardless of other signals; (2) `hasSufficientPositiveSignals` — ip_consistency + post_purchase_consumption + tos_accepted must all be present. `isSufficient()` = not contradicted AND sufficient positive signals. Absent signals are routing concerns, not contradictions; they route to `MANUAL_REVIEW` without implying fraud or legal liability. No probabilistic scoring, ML, or LLM judge introduced. | PRD §3 explicitly lists "Identity Match + IP Consistency + Post-Purchase Consumption" as the strong evidence combination. The prior model incorrectly treated `tos_accepted` and `temporal_sequence_valid` as peer veto signals rather than recognising that `temporal_sequence_valid` is a contradiction detector and `tos_accepted` is a positive signal whose absence is a routing concern. ADR-002 (no complex infrastructure), PRD §3 evidence semantics. |
| **ADR-013** | **Authoritative Application Technology Stack** | The application stack is **Node.js + TypeScript for backend services** and **React + TypeScript for the frontend**. Python is NOT used for application code, backend services, tests, or automation scripts. Milestone 1 was rebuilt in TypeScript after an incorrect Python implementation was removed. The backend package manager is npm. Test framework: Vitest. | The buildathon submission is a web application requiring a React frontend and a Node.js backend. Python is not suitable for this stack. ADR-011 (Python stdlib schemas) is superseded by this decision and by the TypeScript rebuild. |
| **ADR-014** | **Milestone 2 — Synthetic Dataset & Oracle Implementation Decisions** | (1) **PRNG**: xoshiro128\*\* seeded via splitmix32 expansion — pure TypeScript, no external dependencies, reproducible across Node.js versions. (2) **IP ranges**: RFC 5737 documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) and RFC 1918 private ranges — guarantees no real routable IP addresses appear. (3) **Email TLDs**: `.test` and `.invalid` (IANA reserved) — guarantees no real email addresses. (4) **Oracle label table**: `ORACLE_LABEL_TABLE` is a static `Record<ScenarioType, EvalGroundTruth>` constant in `scenarioOracle.ts`. It does not import or call any production routing function. (5) **Holdout diversity**: DEV uses all 8 scenario types with varying proportions; HOLDOUT uses 7 scenario types at equal weight — structurally different distributions prevent near-duplication. (6) **Eval B narrative baseline**: deterministic template string (not LLM) generates clean narratives; fault injection is deterministic text mutation — no random LLM-generated content. (7) **Dataset storage**: in-memory TypeScript modules (`fixtures.ts`) — no database server required at Milestone 2. Dataset is regenerated deterministically at startup. (8) **Merchant DB user count**: 300 users generated for the canonical fixtures module to provide enough bundles for Eval A (150) + Eval B (200) without overlap. | All decisions choose the smallest reasonable option consistent with the planning documents. No database, no external APIs, no complex infrastructure introduced. |
| **ADR-015** | **Milestone 3 — Deterministic Engine Module Design** | (1) **Module separation**: Four focused modules — `evidenceRepository` (DB lookup only), `evidenceVerifier` (consistency checks + signal computation), `router` (routing policy), `stateMachine` (transition table) — orchestrated by `engine/index.ts`. No responsibilities merged. (2) **Milestone 3 terminal state for DEFENDABLE cases**: `SUFFICIENCY_ASSESSED`. The engine stops here; `RESPONSE_DRAFTED` is reserved for Milestone 4 (LLM integration). The engine does NOT pretend a response was drafted. (3) **Identity match check**: `disputeIngest.claimed_user_id === transaction.user_id`. The chargeback payload provides the claimed user ID; the transaction record provides the authoritative user ID. A mismatch is a critical contradiction. (4) **IP consistency**: Evaluated as `transaction.ip_address` matching ANY IP log OR consumption log IP for that user/transaction. As per PRD §3, this is a supporting signal only; NAT/VPN limitations are documented in the reason field. (5) **Multiple consumption logs**: The earliest consumption log timestamp is used for temporal sequence validation. All logs are stored in the snapshot. (6) **Fail-closed on any error**: The `processDispute()` function never throws; all exceptions are caught and converted to `ok:false` `MANUAL_REVIEW` outcomes with structured `failure_reason` and `failure_detail` fields for audit logging. | ARCHITECTURE.md §2 (state machine), §5 (routing matrix), §8 (failure states). PRD §3 (evidence semantics). ADR-012 (sufficiency model). |
| **ADR-016** | **Milestone 4 — Bounded LLM Drafting & Deterministic Validation (Groq API & Strict JSON Schema)** | (1) **Provider**: Groq API (`groq-sdk`) is the authoritative LLM provider. (2) **Default Model**: `openai/gpt-oss-20b`, configurable via `process.env.GROQ_MODEL`. (3) **Credentials**: API key read exclusively from `process.env.GROQ_API_KEY`, never logged or committed. (4) **Strict Structured Output**: Request uses Groq Strict Structured Outputs mode (`response_format.type = "json_schema"`, `json_schema.strict = true`, `additionalProperties: false`, all fields required in schema, nullable fields using union types). (5) **Hard Validator**: Hard deterministic post-generation validator checks structural validity, entity match (transaction_id, user_id, amount, currency, dates, IP), semantic safety (rejecting fraud/intent/legal claims), and ground-truth label references. (6) **Fail-Closed**: Any API error, missing key, timeout, or validation failure routes dispute to `MANUAL_REVIEW`. Rejected drafts are excluded from final evidence package and retained in audit log. | `PRD.md` §3 & §5, `ARCHITECTURE.md` §7, `PROJECT_RULES.md` Rules 7, 8, & 9. |
| **ADR-017** | **Milestone 5 — Audit Trail & PDF Evidence Package Implementation** | (1) **Audit Log**: `AuditLogger` provides an in-memory application-level append-only log enforcing `append` and `retrieve` only (no update or delete APIs). Stores workflow events, state transitions, and retains rejected LLM outputs for auditability with exact semantic wording while excluding them from final evidence packages. (2) **PDF Generator Dependency**: `pdfkit` installed as a lightweight, pure Node.js dependency for rendering structured multi-section PDF buffers in memory without external headless browser overhead (e.g. Puppeteer/Chromium). (3) **Deterministic Package Validation**: `PackageValidator` verifies state boundaries (`RESPONSE_VALIDATED` or `HUMAN_APPROVAL_REQUIRED`), entity alignment (disputed amount, currency, transaction ID), validated draft status, ground-truth isolation (`ground_truth` and oracle label checks), and secret isolation before final package compilation or PDF rendering. | `PRD.md` §2 & §7, `ARCHITECTURE.md` §7, `DATA_MODEL.md` §4, `PROJECT_RULES.md` Rules 6, 7, 8, & 9. |
| **ADR-018** | **Milestone 6 — Evaluation Runner & Measured Benchmark Implementation** | (1) **Non-Circular Evaluation A Architecture**: `EvalACase.ground_truth` is established by the independent scenario oracle during seed-42 dataset generation. Production deterministic routing (`routeDispute`) generates system predictions separately; oracle labels are never overwritten or derived from routing logic. (2) **Evaluation B Test Harness**: Evaluates hard validator (`validateDraft`) safety across 200 controlled test harness samples (100 clean, 100 fault injected) without live Groq network dependency. (3) **Metrics & Export**: Pure metric math functions (`confusionMatrix`, `precision`, `recall`, `f1`, `falsePositiveRate`, `falseNegativeRate`, `manualReviewRate`) operate deterministically without hardcoding target values, exporting machine-readable results to `docs/eval_results.json`. | `PRD.md` §6, `EVALUATION.md` §1-4, `PROJECT_RULES.md` Rule 11 & Rule 12. |
| **ADR-019** | **Milestone 7 — REST HTTP API & Demo Orchestration Architecture** | (1) **HTTP Framework**: Express (`express`) selected as minimal HTTP framework for Node.js + TypeScript REST endpoints. (2) **API Adapter Principle**: Route handlers act purely as adapter orchestration controllers without duplicating any evidence verification, routing rules, or validation logic. (3) **CORS Policy**: Configured strictly for local React development (`FRONTEND_ORIGIN` env var or default `http://localhost:5173`). `*` wildcard prohibited. (4) **Demo Idempotency**: Repeated calls to `/api/disputes/:id/process` on cases already processed past `RECEIVED` return existing state without duplicate state transitions or re-running LLM drafting. (5) **Ground-Truth & Secret Isolation**: API DTOs and log serializers enforce strict field exclusion (`ground_truth`, oracle tables, `GROQ_API_KEY`, tokens). (6) **State Machine Enforcement**: State transitions (`HUMAN_APPROVAL_REQUIRED` -> `READY_FOR_SUBMISSION`, `READY_FOR_SUBMISSION` -> `SUBMITTED`) are strictly controlled by state machine rules, returning HTTP 409 Conflict on invalid state transitions. (7) **Simulated Submission**: Submission endpoint transitions state to `SUBMITTED` locally and returns `is_simulated: true`; no external Razorpay or card network APIs are contacted. | `PRD.md` §2 & §3, `ARCHITECTURE.md` §7, `PROJECT_RULES.md` Rules 2, 3, 5, 7, 8, & 9, Milestone 7 §1–§23. |

## 2. Unresolved Issues & Open Decisions

The following items represent underspecified or ambiguous requirements identified during architecture review. They are recorded here rather than silently resolved:

### Issue 1: Razorpay Webhook Payload Schema Mapping
- **Context:** `PRD.md` §2 specifies ingesting standard incoming JSON webhook payloads. `PROJECT_RULES.md` Rule 2 states "Never invent Razorpay APIs, webhook event names, API fields".
- **Status:** Unresolved.
- **Architectural Approach:** The architecture defines a flexible normalized internal webhook contract (`event`, `dispute_id`, `transaction_id`, `amount`, `currency`, `reason_code`, `chargeback_date`). The external mapping to specific Razorpay webhook headers or fields is recorded as requiring verification prior to live integration.

### Issue 2: LLM API Timeout & Network Error Retry Limit
- **Context:** `PRD.md` §5 defines system failure modes but does not specify network retry limits for Gemini API requests.
- **Status:** Unresolved.
- **Architectural Approach:** Default behavior is Fail-Closed. If the Gemini API call times out or throws an uncaught exception, zero retries will be attempted automatically; the system immediately transitions to `MANUAL_REVIEW`. The rejected attempt is recorded in the application-level append-only audit log.

### Issue 3: PDF Render Dependency Selection
- **Context:** `PRD.md` §2 lists PDF compilation engine as a real boundary component. `PROJECT_RULES.md` Rule 15 prefers the simplest implementation.
- **Status:** Unresolved.
- **Architectural Approach:** The architecture specifies generating clean HTML/CSS evidence reports that can be rendered/saved as PDF directly by the browser or compiled via standard lightweight HTML-to-PDF tools. Final dependency selection awaits user confirmation before Milestone 5.

## 1. Decision Log

| Decision ID | Topic | Decision Made | Rationale & Rule Reference |
|---|---|---|---|
| **ADR-001** | LLM Authority Boundaries | LLM is restricted exclusively to text narrative generation from `VERIFIED_EVIDENCE_SNAPSHOT`. Zero authority to change state, evaluate evidence, route disputes, or approve outputs. | `PRD.md` §4 & `PROJECT_RULES.md` Rules 7 & 8. |
| **ADR-002** | Infrastructure Scope | Single-service architecture without microservices, Kafka, Redis, Celery, RAG, or vector DBs. | `PROJECT_RULES.md` Rule 5 ("Never add microservices, Kafka..."). |
| **ADR-003** | Fail-Closed Handling | Any missing evidence, contradictory telemetry, entity validator rejection, or runtime crash immediately forces state to `MANUAL_REVIEW`. | `PRD.md` §5 & `PROJECT_RULES.md` Rule 9 ("If validation fails: FAIL CLOSED -> MANUAL_REVIEW"). |
| **ADR-004** | External Gateway Submissions | External dispute submissions are modeled as SIMULATED. Approval transitions `HUMAN_APPROVAL_REQUIRED` -> `READY_FOR_SUBMISSION` (generating PDF package). A separate action transitions `READY_FOR_SUBMISSION` -> `SUBMITTED` internally; no live bank APIs are called. | `PRD.md` §2 & `PROJECT_RULES.md` Rule 2 & Rule 3 ("Never invent Razorpay APIs... mark as simulated"). |
| **ADR-005** | IP Telemetry Semantics | IP/device consistency is treated strictly as a supporting signal, not as absolute proof of identity or fraud. | `PRD.md` §3 & §11 (Q&A Defense #5). |
| **ADR-006** | Metric Measurement Boundary | Benchmark metrics formulas are documented in `EVALUATION.md`. Target numbers will only be recorded after executing evaluation scripts during Milestone 6. | `PROJECT_RULES.md` Rule 11 ("Never report target metrics as measured results"). |
| **ADR-007** | Non-Circular Evaluation A Ground Truth | Evaluation A ground-truth labels (`DEFENDABLE` / `NOT_DEFENDABLE`) are generated by an independent synthetic scenario oracle during dataset creation, *completely isolated from and prior to executing the production routing function*. | Fixes circular evaluation by ensuring system routing output is evaluated against pre-established independent labels. |
| **ADR-008** | Semantic Fact Validation | The LLM response contract strictly prohibits claims of customer intent ("intentionally committed fraud"), legal conclusions, or fraud certainty. Hard validator rejects any draft containing unsupported inferences without adding second LLM judges or RAG pipelines. | Preserves simplicity (Rule 15) while enforcing strict safety boundaries (Rule 7 & 8). |
| **ADR-009** | Standardized Money Representation | Financial amounts across data schemas, API payloads, synthetic datasets, LLM prompts, and UI are represented consistently as **major currency units** (e.g. `amount = 4999` with `currency = "INR"` represents ₹4,999). | Eliminates major/minor unit ambiguity across system components. |
| **ADR-010** | Audit Log Retention & Terminology | The system implements an application-level append-only audit log with no update or delete operations for historical entries. Rejected LLM outputs are retained in the audit log for traceability rather than being destroyed. | PRD §7 & auditability compliance. Exact wording: "The invalid output is excluded from the final evidence package and cannot progress through the workflow; the rejected output is retained in the append-only audit log for traceability." |

## 2. Unresolved Issues & Open Decisions

The following items represent underspecified or ambiguous requirements identified during architecture review. They are recorded here rather than silently resolved:

### Issue 1: Razorpay Webhook Payload Schema Mapping
- **Context:** `PRD.md` §2 specifies ingesting standard incoming JSON webhook payloads. `PROJECT_RULES.md` Rule 2 states "Never invent Razorpay APIs, webhook event names, API fields".
- **Status:** Unresolved.
- **Architectural Approach:** The architecture defines a flexible normalized internal webhook contract (`event`, `dispute_id`, `transaction_id`, `amount`, `currency`, `reason_code`, `chargeback_date`). The external mapping to specific Razorpay webhook headers or fields is recorded as requiring verification prior to live integration.

### Issue 2: LLM API Timeout & Network Error Retry Limit
- **Context:** `PRD.md` §5 defines system failure modes but does not specify network retry limits for Gemini API requests.
- **Status:** Unresolved.
- **Architectural Approach:** Default behavior is Fail-Closed. If the Gemini API call times out or throws an uncaught exception, zero retries will be attempted automatically; the system immediately transitions to `MANUAL_REVIEW`. The rejected attempt is recorded in the application-level append-only audit log.

### Issue 3: PDF Render Dependency Selection
- **Context:** `PRD.md` §2 lists PDF compilation engine as a real boundary component. `PROJECT_RULES.md` Rule 15 prefers the simplest implementation.
- **Status:** Unresolved.
- **Architectural Approach:** The architecture specifies generating clean HTML/CSS evidence reports that can be rendered/saved as PDF directly by the browser or compiled via standard lightweight HTML-to-PDF tools. Final dependency selection awaits user confirmation before Milestone 5.

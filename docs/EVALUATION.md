## 1. Evaluation Paradigm & Separation of Concerns

To prevent conflating deterministic evidence routing with LLM output safety, evaluation is strictly divided into two independent benchmarks:

- **Evaluation A:** Benchmark of the **Deterministic Evidence Routing Engine**.
- **Evaluation B:** Benchmark of the **Post-Generation Hard Validator (LLM Safety)**.

Per `PROJECT_RULES.md` Rule 11, target metrics are framework specifications and must NEVER be reported as measured results prior to running evaluation scripts.

---

## 2. Evaluation A: Evidence Routing Performance (Non-Circular Oracle Benchmark)

### 2.1 Independent Ground Truth Oracle Definition
To guarantee non-circularity, Evaluation A ground-truth labels (`DEFENDABLE` vs `NOT_DEFENDABLE`) are generated by an **independent synthetic scenario oracle** during dataset creation, *completely isolated from and prior to executing the production routing function*.

```text
Synthetic Scenario Oracle Assignment:
1. Scenario Parameters defined (User identity, IP consistency, TOS log, Consumption log, Timestamps).
2. Oracle assigns Ground-Truth Label independently:
   - Strong telemetry (Identity + Matching IP + TOS + Usage + Valid Timestamps) -> DEFENDABLE
   - Missing or contradictory telemetry -> NOT_DEFENDABLE
3. Production Routing Engine is invoked separately to produce System Routing Output.
4. Evaluation measures: INDEPENDENT GROUND TRUTH vs SYSTEM ROUTING OUTPUT.
```

The production routing function is NEVER used to construct expected labels. Ground-truth labels are established before system evaluation begins.

### 2.2 Dataset Specifications
- **Total Dataset Size:** 150 synthetic dispute cases.
- **Random Seed:** Reproducible random seed `seed = 42`.
- **Split Ratio:**
  - **70% Development Set:** 105 cases (used for rule tuning and sanity testing).
  - **30% Held-Out Evaluation Set:** 45 cases (strictly isolated; never used for tuning or demo cases).

### 2.3 Operational Mapping & Confusion Matrix

| Independent Ground Truth Label | System Routing Outcome | Classification | Operational Cost / Impact |
|---|---|---|---|
| `DEFENDABLE` | Response Generated / Eligible for Approval (`HUMAN_APPROVAL_REQUIRED`) | **True Positive (TP)** | Optimal workflow; analyst time saved. |
| `DEFENDABLE` | Routed to `MANUAL_REVIEW` (No draft) | **False Negative (FN)** | Wasted analyst compilation time; backlog risk. |
| `NOT_DEFENDABLE` | Routed to `MANUAL_REVIEW` (Blocked from AI) | **True Negative (TN)** | Safe defensive handling; avoids bad disputes. |
| `NOT_DEFENDABLE` | Response Generated / Eligible for Approval | **False Positive (FP)** | High operational risk; analyst time wasted on un-defendable dispute. |

### 2.4 Mathematical Metrics Formulas
- **Precision:** $\text{Precision} = \frac{TP}{TP + FP}$
- **Recall:** $\text{Recall} = \frac{TP}{TP + FN}$
- **F1 Score:** $\text{F1} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$
- **False Positive Rate (FPR):** $\text{FPR} = \frac{FP}{FP + TN}$
- **False Negative Rate (FNR):** $\text{FNR} = \frac{FN}{TP + FN}$

## 3. Evaluation B: LLM Output Safety & Hard Validator Benchmark

### 3.1 Purpose & Scope
Evaluates the capability of the Post-Generation Hard Validator to catch unsupported claims, hallucinated entities (dates, IPs, amounts in major currency units, IDs), and unsupported inferences (e.g. claims of customer intent or legal fraud certainty) generated by or injected into LLM narratives.

### 3.2 Test Harness Specifications
- **Total Test Cases:** 200 controlled test harness samples.
- **Composition:**
  - **100 Clean Valid Outputs:** Genuinely accurate LLM narratives matching `VERIFIED_EVIDENCE_SNAPSHOT` 100%.
  - **100 Injected Corrupted Outputs (Fault Injection Harness):** Outputs explicitly mutated with unsupported facts or inferences:
    - *Date Mutation:* e.g. Purchase date shifted from `2026-09-01` to `2029-12-01`.
    - *IP Fabrication:* e.g. Submitting non-matching IP `10.99.88.77`.
    - *Amount Alteration:* e.g. Transaction amount in major currency units altered from `4999 INR` (₹4,999) to `99999 INR` (₹99,999).
    - *Identifier Hallucination:* Fabricating user email or transaction ID.
    - *Unsupported Intent Inference:* Injecting phrases like "The customer intentionally committed fraud."

### 3.3 Safety Metrics Definitions
- **Unsupported-Claim Detection Rate:**
  $$\text{Detection Rate} = \frac{\text{Corrupted Outputs Caught and Rejected}}{\text{Total Corrupted Outputs (100)}} \times 100\%$$
- **False Acceptance Rate (FAR):**
  $$\text{FAR} = \frac{\text{Corrupted Outputs Bypassing Validator}}{\text{Total Corrupted Outputs (100)}} \times 100\%$$
  *(Target: 0.0%)*
- **Validation Pass Rate on Clean Data:**
  $$\text{Pass Rate} = \frac{\text{Clean Outputs Passed by Validator}}{\text{Total Clean Outputs (100)}} \times 100\%$$

## 4. Evaluation Runner Execution Command

The evaluation benchmark is executed via a deterministic test script:

```bash
# Execute Evaluation A and Evaluation B benchmarks
python -m tests.eval_runner --seed 42 --export-metrics docs/eval_results.json
```

Outputs metrics in JSON and prints standard confusion matrices without hardcoding results.
